# Building Aven-1: a language model from random weights

Aven-1 is a causal Transformer trained from scratch — no pretrained weights, no external API, no downloaded model — on an 8 GB M2 MacBook Air. This is a write-up of what was actually built and, more usefully, what broke along the way and what fixing it taught.

## What's in the pipeline

Every stage a real language model goes through, built by hand at a scale a laptop can run:

- **A from-scratch byte-pair encoding tokenizer** (`tokenizer.py`) — the same merge-the-most-frequent-pair algorithm GPT-2 uses, trained on the project's own corpus, not downloaded.
- **Pretraining** on six public-domain books (~2.2 MB: *Alice in Wonderland*, *Pride and Prejudice*, *Sherlock Holmes*, *Frankenstein*, *The Time Machine*, *A Christmas Carol*), teaching general English structure.
- **Instruction fine-tuning** on a programmatically generated dataset (`make_instructions.py`) — arithmetic, antonyms, calendar facts, small talk, book trivia, sentence continuation, and an explicit "I don't know" fallback category — teaching the model to answer instead of just continuing text.
- **A chat interface** (`chat.html`) and a full training dashboard (`ui.html`) — sidebar navigation, live loss charts, a training-data workspace, and SQLite-backed notes storage kept explicitly separate from the model's learned weights.
- **Real experiment tracking**: Weights & Biases logging loss, held-out perplexity, gradient norm, weight norm, per-layer gradient/weight histograms, throughput, and a live table of sample generations that updates during training.
- **A hyperparameter sweep** (`sweep.yaml`) — 31 automated runs searching learning rate, dropout, and batch size, with W&B's parallel-coordinates view showing learning rate as the dominant factor for held-out perplexity.
- **A free cloud GPU path** (`Aven-1-Colab.ipynb`) — the identical training code running on a Colab T4 GPU instead of the M2's CPU/MPS, verified end to end: trained remotely, downloaded, and continued locally without incident.
- **RLHF, in progress** (`preferences.py`, `reward_model.py`, `train_reward.py`, `raft.py`, `ppo.py`, `value_model.py`) — real human preference collection, a reward model, RAFT (reward-ranked fine-tuning), and a full PPO implementation with PPO-ptx (value network, GAE, clipped objective, KL penalty, pretraining-loss anchor); see below for what building each against real, limited data revealed.

Current model: 19.8M parameters (512-wide, 6 layers, 8 heads, 192-token context, 1,536-token vocabulary), fine-tuned through five iterations on progressively larger and more diverse instruction data (6,000 → 17,400 examples).

## What actually broke, and what it taught

The interesting part isn't that this worked — it's the failures, because each one is a real, generalizable lesson rather than a tutorial step.

**Hyperparameters don't transfer across model scale.** The sweep found a strong learning rate (~0.003) on a small 601K-parameter proxy model used for fast search. Applying that same rate directly to the real 19.8M-parameter model caused visible instability — perplexity climbed instead of falling, and the resulting checkpoint generated garbled text. The fix wasn't more tuning; it was recognizing that a learning rate optimal for one model size can actively destabilize a larger one, and reverting to a conservative, previously-validated rate. This is a known phenomenon in the literature (motivating techniques like µP for hyperparameter transfer) — encountering it firsthand, by breaking a model and diagnosing why, is a different kind of understanding than reading about it.

**A model that "doesn't know" an answer is a data problem, not a model problem.** Early on, asking the model anything outside its training patterns caused it to hallucinate a garbled, malformed response — it had no way to express uncertainty. The fix was adding an explicit fallback category to the training data: varied unfamiliar-sounding questions paired with an honest "I don't have a reliable answer for that" response. This is the same principle behind why real assistant models are trained to refuse or hedge — it has to be taught, not assumed.

**Category imbalance silently caps what a model learns, even with correct data.** Antonym questions kept returning the fallback answer instead of a real one, despite antonym examples being present in the training set. The cause wasn't a model limitation — it was that antonyms made up roughly 1.5% of the training corpus against arithmetic's ~29%, meaning the model saw them far too rarely to learn the pattern reliably. Reweighting the category (not changing the model at all) fixed it completely.

**Formal training data does not generalize to how people actually type.** The model handled "What is 4 plus 9?" correctly but broke completely on "whats 1+1" or "hello introduce yourself" — real casual phrasing (lowercase, no punctuation, contractions, combined requests) that never appeared in the clean, grammatically formal training examples. The fix was systematic: a `casualize()` transform applied to a majority of training categories, teaching the same correct response regardless of formal or informal phrasing.

**Small models memorize arithmetic; they don't compute it.** After all fixes, formal-phrasing arithmetic ("What is 4 plus 9?") is reliably correct, but compact notation ("1+1") produces plausible-looking, consistently wrong answers. This is an honest architectural ceiling at this scale, not a bug — the model is pattern-matching against memorized examples, not performing arithmetic. Real arithmetic capability in language models is understood to be an emergent property of much larger scale, not something a 20M-parameter model trained on a few thousand examples can be expected to have.

## Scaling up: bigger isn't automatically better at a fixed step count

After the pipeline above stabilized on a 19.8M-parameter fine-tuned model, a separate pretraining track tested scale directly: a 58,424,832-parameter model (768-wide, 8 layers, 12 heads) was pretrained on the same six-book, 2.2 MB corpus, then a second, larger 153M-parameter model (1024-wide, 12 layers, 16 heads) was pretrained from scratch on the identical corpus and tokenizer settings, both on a free Colab T4 GPU.

In this **matched-step** comparison (1000 optimizer steps per model), the larger model had higher held-out loss and perplexity. This is not a matched-compute comparison: the models require different amounts of computation per step, and total FLOPs were not measured:

| Model | Parameters | Step | Held-out loss | Held-out perplexity |
|---|---|---|---|---|
| Pretrain A | 58.4M | 1000 | 5.551 | 257.56 |
| Pretrain B | 153M | 1000 | 5.791 | 327.4 |

This isn't a bug or a regression — it's the expected behavior when model size scales up but data and step count don't: a larger model has more parameters to fit against the same roughly 640K training tokens and the same fixed learning rate (3e-4, untuned for the new size), so it takes more gradient steps to reach the same point on the loss curve, independent of its higher ceiling. The 58.4M model, given more steps afterward (2100 total, still on the same fixed corpus), continued falling to a held-out perplexity of 172.07 — well past its own step-1000 mark — which is the more useful comparison than a snapshot at one arbitrary step count.

This is a single-run, single-seed result at a small scale and isn't a general claim about scaling laws — it's a concrete, reproducible instance of the well-known distinction between *model capacity* and *training progress*: a bigger model's advantage shows up in its eventual floor, not necessarily at a fixed step count on a fixed-size dataset, and especially not when the learning rate was tuned for a different model size (see the earlier LR-transfer finding above). The natural next step is running the 153M model well past 1000 steps on the same corpus to see whether it eventually surpasses the 58M model's 172.07 floor, and whether learning-rate retuning for the larger width changes the comparison.

**Kaggle continuation incident record (2026-09-09; metrics only).** Ari reported that the 58,424,832-parameter continuation reached step **3560**, with train loss approximately **3.45** and held-out loss approximately **4.914**, before the checkpoint was lost with Kaggle's no-persistence session. No usable checkpoint from that endpoint has been verified; these numbers must not be presented as a resumable or independently reevaluated model.

A read-only recovery of the [shared W&B run](https://wandb.ai/ariveinberg-ari-research/aven-1/runs/pretrain-096ba20e-52bb62a7) found two distinct records: the history row at model step 3560 contains train loss **3.447188377380371**, held-out loss **4.912829279899597**, and held-out perplexity **136.02**; the final summary contains `final_step=3560` and `final_val_loss=4.914183259010315`. The summary and history are not a single consistent evaluation, and concurrent writers prevent unambiguous platform attribution from run ID alone. Preserve both; do not attach the history perplexity to the different final-summary loss. The old Kaggle notebook also retains a later assertion failure, `Expected step 2100; found 4000`; this is evidence of a reported checkpoint step at that time, not evidence of a surviving step-4000 artifact or its metrics. Step 3560 is therefore a preserved observation, not a proven maximum step. See [issue #1](https://github.com/ariveinberg-max/aven-1/issues/1). Equal optimizer steps across 58M and 153M models are a matched-step comparison, not matched compute.

## The corpus was badly undersized relative to the models trained on it

Chinchilla's compute-optimal scaling result (Hoffmann et al., 2022) recommends roughly 20 tokens of training data per model parameter. The six-book, 640,821-token corpus used for every pretraining run above is wildly short of that: the 58M-parameter model would want ~1.17 billion tokens under that rule, and the 153M model ~3 billion — both models were training on roughly 0.02-0.05% of their compute-optimal data budget, effectively re-reading the same six books dozens of times rather than seeing new information. This is a real, avoidable version of the "ignoring the Chinchilla math" mistake, not a discovery specific to this project.

The fix, applied before any further paid GPU time is spent: the corpus was expanded from six books (2,226,235 bytes) to 23 books (17,913,943 bytes) by adding 17 more public-domain novels from Project Gutenberg (*Moby-Dick*, *Dracula*, *The Picture of Dorian Gray*, *Adventures of Huckleberry Finn*, *Little Women*, *The Wonderful Wizard of Oz*, *Treasure Island*, *A Tale of Two Cities*, *The Strange Case of Dr Jekyll and Mr Hyde*, *Jane Eyre*, *Wuthering Heights*, *The Call of the Wild*, *Anne of Green Gables*, *Great Expectations*, *Gulliver's Travels*, *The Count of Monte Cristo*, *War and Peace*) — an 8x increase, still far short of compute-optimal at this model size, but a meaningful move in the right direction before spending money on longer training runs against the old, thin corpus.

**Third expansion (2026-09-09): 59 books (~40MB) to Simple English Wikipedia added (~316MB extracted, ~354MB total corpus).** Full English Wikipedia's dump is ~20GB compressed (roughly 80-90GB of raw article text) — impractical to fetch/process/tokenize-train on in a single session on this hardware. Simple English Wikipedia is the same encyclopedia written in simpler language, with a ~356MB compressed dump — a real, tractable jump in factual/encyclopedic diversity, directly addressing the "zero real-world facts" gap found when the model answered "who was the first president" with nonsense before any factual training data existed. Downloaded via `dumps.wikimedia.org` (requires a descriptive User-Agent header per Wikimedia's dump-access policy; a generic client gets HTTP 403) and parsed from scratch (no `wikiextractor` dependency, consistent with this project's build-it-yourself approach): strips templates/infoboxes (`{{...}}`, brace-depth-aware to handle nesting), tables (`{|...|}`), `<ref>` citations, HTML comments/tags, and converts `[[link|display]]` wiki-links to their display text. 218,364 articles extracted (114,981 redirects correctly skipped), ~316MB of clean prose, in about 4 minutes. Known minor imperfection: a small fraction of articles retain a leftover fragment from nested image-caption links (e.g. a trailing `"...Northern Hemisphere.]]"`) where the file-link stripping regex didn't fully match a nested pattern — acceptable noise level, not pursued further given time constraints. Combined corpus: 38,516,269 -> 354,359,702 bytes. The 2GB corpus-workspace cap (`sources.py`) was raised again (from 200MB) to accommodate this and further planned growth.

**The training pipeline itself couldn't actually handle a corpus this size — two separate bottlenecks, both fixed (2026-09-09).** Wanting to eventually train on full (not just "Simple") English Wikipedia — a ~20GB compressed dump, ~15-20GB of cleaned text — exposed that `train.py` and `tokenizer.py` were never built for anything beyond tens of MB:

1. **Memory**: `train.py` read the entire corpus into a Python string, decoded it, and held every token as an int64 in one big tensor. At 354MB this already used real memory; at Wikipedia's 15-20GB scale it would need far more RAM than an 8GB Mac has, regardless of patience. Fixed by rewriting the pipeline to stream: the corpus is hashed and UTF-8-validated in chunks (`stream_fingerprint_and_validate`), the tokenizer trains on a bounded 20MB sample rather than the whole file (sufficient for learning merge statistics), and the full corpus is encoded chunk-by-chunk into an on-disk `uint16` binary cache, then accessed during training via `numpy.memmap` — the OS pages in only the small random windows each training step actually touches, never the whole file. Verified against the real 354MB corpus: peak memory **~1.9GB**, versus an estimated several-GB-plus under the old approach (and outright infeasible at Wikipedia scale).

2. **Speed**: `tokenizer.py`'s `encode_ids()` did one full pass over the entire corpus *per learned merge rule* (~1,800 merges at this project's vocab size) — O(corpus_size × merge_count). This is why encoding the 17.9MB corpus took ~14 minutes; at Wikipedia scale it would have taken an estimated **days**, independent of the memory fix. Replaced with a standard O(n log n) algorithm: a doubly-linked list over token positions plus a min-heap of candidate merges ordered by learned rank, with lazy invalidation of stale heap entries when a position's neighbors change. Verified to produce byte-identical output to the original sequential algorithm on multiple real text samples and edge cases (empty input, single/double bytes), with a measured **30x speedup** at this project's actual vocab size (2048) on a real 414KB sample — and the speedup ratio grows with corpus size, since the old algorithm scales with corpus size × merge count while the new one scales with corpus size × log(corpus size). Encoding the real 354MB corpus end-to-end (tokenizer training + full encode) took **~21 minutes** with the fixed pipeline, versus an extrapolated multi-hour-to-day range with the original.

One accepted tradeoff: encoding happens in 8MB chunks, so a merge that would span exactly across a chunk boundary is missed (~44 boundaries across the 354MB corpus). This never corrupts data — decoding the chunked encoding still reconstructs the original text exactly (verified in `test_streaming.py`) — it just occasionally leaves a boundary byte-pair one merge less compressed than a true single-pass encode would. Both fixes are covered by new automated tests (`test_tokenizer.py`, `test_streaming.py`) rather than only the manual smoke test described here. Full, uncapped English Wikipedia itself has not yet been attempted — this work makes it *possible* without crashing or taking days, not something already run end-to-end.

**Second expansion (2026-09-09): 23 books (17,913,943 bytes) to 59 books (39,987,621 bytes).** After the RunPod run below showed the 153M model was still cycling through the same ~5M-token corpus roughly six times over by step 20,540, 36 more public-domain works were added — this time deliberately spanning genres beyond Victorian novels, since the first expansion was still fiction-only: Homer's *Iliad* and *Odyssey*, philosophy (Plato's *Republic*, Marcus Aurelius's *Meditations*, Machiavelli's *The Prince*, Nietzsche's *Beyond Good and Evil* and *Thus Spoke Zarathustra*, Thoreau's *Walden*), Darwin's *On the Origin of Species*, Shakespeare (*Hamlet*, *Macbeth*, *Romeo and Juliet*), poetry (Whitman's *Leaves of Grass*), history/politics (*The Federalist Papers*, Paine's *Common Sense*, Du Bois's *The Souls of Black Folk*), plays (Wilde's *The Importance of Being Earnest*, Ibsen's *A Doll's House*), more novels (Twain's *Tom Sawyer* and *The Prince and the Pauper*, Defoe's *Robinson Crusoe*, three more Wells novels, three more Austen novels, Eliot's *Middlemarch* and *Silas Marner*, Hawthorne's *The Scarlet Letter*, three more Sherlock Holmes novels, two more Verne novels, *Grimms' Fairy Tales*, and Hugo's *Les Miserables*). Still well short of Chinchilla-optimal for a 153M-parameter model (roughly 11.5M tokens against a ~3 billion token target), but a real, deliberate step toward genre diversity, not just more volume of the same kind of text — worth remembering that raw data volume is not the only axis "undersized" can mean.

## The "held-out" evaluation set wasn't actually held out

Every held-out perplexity number reported above (172.07, 327.4, 84.88, and any that follow from `train.py`'s internal split) came from the same mechanism: `train.py` encodes the full `data/training.txt` corpus and takes `data[:int(len(data)*0.9)]` as training and the remaining last 10% as "validation." That last 10% is not a separate, independently-sourced test set -- it's a contiguous slice of the same 58-59 books, same authors, same era of prose, same tokenizer statistics. A model can score well there partly by having absorbed the stylistic and lexical regularities of the other 90%, not purely by generalizing to genuinely unseen text. None of the perplexity numbers in this document are wrong, but they're all measuring something closer to "how well does the model fit this corpus's overall style" than "how well does the model predict text it has never trained on."

**Fix applied (2026-09-09):** two books were pulled out of `data/sources/` entirely, into a new `data/eval-heldout/` directory that `sources.compile_corpus()` never reads, and `data/training.txt` was recompiled without them (39,987,621 -> 38,516,269 bytes, a 1,497,825-byte reduction, about 3.7% of the pre-holdout corpus). A checkpoint trained from this point forward has seen zero tokens of either file, ever.

The two books were chosen to test two different things:

- **`sign-of-four.txt`** (Arthur Conan Doyle, *The Sign of the Four*, 241,390 bytes) tests generalization *within* a well-represented style -- three other Conan Doyle works (`sherlock-holmes.txt`, `study-in-scarlet.txt`, `hound-of-baskervilles.txt`) stay in training, so the model has plenty of exposure to this author's vocabulary, sentence structure and genre (Victorian detective fiction) without ever seeing this specific book. This is the harder and more informative test: a bad score here would suggest genuine overfitting to the training set's specific sequences rather than its style.
- **`moby-dick.txt`** (Herman Melville, 1,256,435 bytes) tests generalization to an author and voice with zero other representation in the corpus. This is the easier, more interpretable baseline: a bad score isn't surprising (Melville's digressive, essayistic first-person voice is unlike anything else in the corpus), but a good score would be a real, notable finding about the model's generalization rather than an artifact of stylistic overlap.

A short read-only script, `eval_heldout.py`, scores a checkpoint against both files with a full, non-overlapping pass (not train.py's random-batch sampling, so the number is reproducible run to run) and reports per-file and combined loss/perplexity. It hasn't been run against any checkpoint yet as part of this change -- no evaluation numbers are being claimed here, only that the measurement now exists and is honestly separated from the training data. `data/eval-heldout/README.md` documents the rationale and the rule to keep future changes honest: if these files are ever moved back into `data/sources/`, that has to be logged here, or every subsequent "held-out" number becomes silently incomparable to what came before.

This is a distinct thing from Codex's `evaluate_capabilities.py`, which measures task capability. This measures whether the model's language-modeling loss is meaningfully worse on text it never trained on at all, versus a held-back slice of text it effectively did train on the neighborhood of. Audited alongside this change: all 58 remaining `data/sources/` files (plus the 2 moved out, 60 total) were checked pairwise by MD5 hash and by title/author -- no duplicate or overlapping-edition content was found; all 60 are distinct works. (One unrelated data-quality note surfaced during the audit: `origin-of-species.txt` still carries a leftover Project Gutenberg "several editions of this ebook" boilerplate header from imperfect stripping -- cosmetic, not a duplication issue, left as-is since fixing corpus text formatting is out of scope here.)

## RLHF, in progress

The fine-tuning above teaches the model to imitate one written example per prompt. RLHF goes further: it optimizes the model directly against actual human preference, which is closer to why models like ChatGPT feel helpful rather than just "trained on good examples." Three pieces, built and tested against real data, not simulated:

- **Preference collection** (`preferences.py`, a Preferences tab in the dashboard): the model generates two responses to the same prompt at different sampling temperatures, a real person picks which is actually better or calls it a tie. No synthetic or self-labeled preferences — that would defeat the entire premise.
- **A reward model** (`reward_model.py`, `train_reward.py`): the same Transformer architecture, initialized from the fine-tuned checkpoint's own weights via transfer learning, with a scalar "how good is this" head replacing the next-token head. Trained on real comparisons via the Bradley-Terry pairwise loss.
- **RAFT** (`raft.py`) — Reward-rAnked FineTuning: a real, published simplification of full RLHF. Full RLHF optimizes via PPO (a value network, a clipped policy objective, a KL penalty against a reference model) — meaningful additional machinery for a 20M-parameter model. RAFT instead generates several candidates per prompt, keeps only the one the reward model scores highest, and fine-tunes on the winners — same direction, without PPO's complexity.

**What labeling only 51 real comparisons revealed, immediately:** 44 of them (86%) came back as ties. Not because the tool was broken — because most of the prompts hit categories the model already answers with extremely peaked confidence (arithmetic, antonyms, calendar facts), so both sampled responses were identical regardless of temperature, even at an extreme 0.4-vs-1.4 gap. There was no preference signal to collect on those. The fix was picking prompts genuinely outside anything the model was drilled on — creative writing, opinions, open-ended questions — where real uncertainty exists.

**Running the reward model and RAFT on only 6 real comparisons confirmed the obvious risk, concretely.** Held-out accuracy read "100%" — meaningless with a single held-out example and a 19.8M-parameter model trivially memorizing 6 training pairs (loss went to exactly 0.000). Running RAFT with that reward model didn't just produce a weak result — it confidently selected outputs like *"on the barrow window"* and *"The month after Tue is Aprise."* as the "best" response to real prompts. The pipeline was working exactly as built; the data feeding it wasn't sufficient yet, and the model happily optimized toward noise. That's now a hard guardrail in `raft.py`: it refuses to run against a reward model trained on fewer than 20 comparisons without an explicit `--force`.

**Even after fixing the prompt pool, the tie-rate problem had a second, subtler layer.** The obvious fix — using genuinely novel prompts the model wasn't drilled on — traded one failure for another: creative-writing prompts (stories, poems, extended descriptions) produced *decisive but incoherent* comparisons, because this model was only ever fine-tuned on 1-2 sentence responses and has no real capability for extended prose at any temperature. The actual fix was a third category: prompts trained with *multiple* valid replies each (identity, greetings, well-being) rather than one canned answer per question — these gave real, coherent, judgment-worthy variance without asking the model to do something it structurally can't.

**With 150 real comparisons (42 decided), the reward model showed genuine signal for the first time:** held-out accuracy of 87.5%, stable across 400 training steps rather than collapsing back to the 50% random baseline. Running RAFT with that reward model correctly selected the coherent, appropriate answer for every category the model actually has competence in (identity, greetings, thanks, help, goodbye) — a real, verified improvement, confirmed by testing the fine-tuned result directly rather than assuming it worked. But it also surfaced an important limit of RAFT itself: for prompts where *none* of the candidates were actually good (genuinely novel opinion questions the model has no real answer for), reward-ranking just picks the least-bad wrong answer — and fine-tuning on that would teach the model to confidently and consistently give one specific wrong answer, which is worse than its current varied wrong behavior. The fix was filtering the RAFT output to only the categories where the reward model's winners were verified to be actually correct before fine-tuning on them, rather than trusting the ranking blindly.

This stage is intentionally left mid-flight rather than pushed to a fake finish: RLHF's entire premise depends on real, sufficient human preference data, and that can't be rushed or synthesized without defeating the point. (Deliberately: no automated or AI-generated preference labels were used anywhere in this — that would be a different, weaker technique called RLAIF, not what's documented here.)

## Full PPO, and the tradeoff it forced into the open

RAFT approximates RLHF's direction without its machinery. The actual algorithm behind InstructGPT/ChatGPT is PPO (Proximal Policy Optimization): a policy network, a value network estimating expected future reward per token, Generalized Advantage Estimation, a clipped surrogate objective, and a KL penalty against a frozen reference model so the policy can't drift into gibberish that scores well but means nothing. All of it implemented (`ppo.py`, `value_model.py`), not approximated further — this project's rule throughout has been to build the real mechanism and report what actually happens, not what should happen in theory.

**First real run exposed a genuine, literature-documented failure mode.** With plain PPO — no anchoring beyond the KL term — rollouts were correctly bounded (KL stayed under 1.3, nowhere near collapse) and the loss curves looked entirely healthy. But comparing actual generations before and after told a different story: **arithmetic broke completely** ("What is 4 plus 9?" went from the correct "13" to an unrelated "Of course, go ahead.") — a category PPO never even rolled out on. The cause: PPO updates the entire shared 19.8M-parameter backbone from whatever narrow slice of prompts it's currently training on, so pushing hard on one slice (identity/greeting prompts, here) can quietly disturb everything else, independent of whether the KL-to-reference stays small. InstructGPT's own paper documents exactly this and fixes it with what they call **PPO-ptx**: mixing the original pretraining loss back into every PPO update, so gradients keep getting pulled toward the network's original broad competence at the same time they optimize for reward.

**Implementing PPO-ptx and sweeping its one real hyperparameter (the mix-in coefficient) produced a complete, honest result — not a clean win, but a real one:**

| `ptx_coef` | Outcome |
|---|---|
| 0 (no anchor) | Catastrophic: arithmetic broken, an untouched category damaged |
| 0.05 | Partial: some categories broke (identity responses truncated mid-sentence, "Goodbye" produced garbled hallucinated text, calendar answers corrupted), others (arithmetic, most greetings) survived intact |
| 1.0 | Zero regression — 8 of 9 tested prompts produced byte-identical output to before PPO — but also zero meaningful learning; the anchor term (~0.2-0.35 in magnitude) fully dominated the actual policy gradient (~0.0001-0.05 in magnitude) |

No coefficient tested here both avoided regression and produced meaningful improvement. That is the actual, verifiable conclusion, and it's consistent with the literature: PPO is known to need substantially more preference data than a method like RAFT to be stable, precisely because it optimizes the whole network directly and continuously rather than doing targeted supervised fine-tuning on a small set of verified-good examples. 34 real comparisons is enough to train a reward model with genuine signal (87.5% held-out accuracy) and enough for RAFT to safely improve specific, verified categories — it is not enough to safely drive full PPO. None of the three PPO checkpoints from this experiment were promoted; they're preserved under `checkpoints-ppo-experiments/` as evidence, and the real, working model in `checkpoints/` is the RAFT-improved one from the previous section.

## Honest scope

This is not a ChatGPT competitor and was never intended to be. It's a demonstration — and a real one, not a toy that fakes the stages — of what building a language model from first principles actually involves: a tokenizer trained from scratch, a real pretrain→fine-tune pipeline, honest evaluation via held-out perplexity, a genuine hyperparameter search with reproducible findings, and a debugging process where every fix came from a diagnosed cause, not guesswork. Closing the remaining gap to something like ChatGPT is a difference of roughly four to five orders of magnitude in parameters, data, and compute — a gap of infrastructure and resources, not of understanding the underlying method.

## RLHF pipeline vs. the new 58.4M model (2026-09-09)

The RLHF pipeline above (`preferences.py`, `reward_model.py`, `train_reward.py`, `raft.py`, `ppo.py`, `value_model.py`) was built and verified against the old, now-superseded 19.8M-parameter model. The working model is now a 58,424,832-parameter finetune (`checkpoints/latest.pt`, width 768/8 layers/12 heads/context 192, vs. the old model's smaller config). Checked whether the pipeline actually transfers, without training anything:

- **No hardcoded dimensions anywhere in the chain.** `RewardModel`, `ValueModel`, `raft.py`, and `ppo.py` all build their config via `Config(**saved['config'])` off the real checkpoint, the same way `server.py` does — nothing assumes the old model's width/layers/heads. Constructing a `RewardModel` from the real 58M checkpoint's config and calling `load_backbone()` on its weights copies 100 of 102 tensors (only `reward_head.weight`/`reward_head.bias` are new, as expected — everything else, including `output.weight`, matches by name/shape) and produces a working 58,425,601-parameter reward model that runs a forward pass cleanly. The pipeline is architecture-agnostic and ready to use against the new model with no code changes.

- **Retested `PREFERENCE_PROMPTS` live against the running model**, via `/api/preferences/pair`'s actual 0.5/0.9 temperature pair (not a guessed 0.4/1.4), two full passes over the old 19-prompt list. Tie rate came back 42.1% (8/19) and 63.2% (12/19) — averaging ~53%, well down from the old model's 86%, but not evenly: six prompts (`Introduce yourself`, `Who are you?`, `Can you help me?`, `Goodbye`, `See you later`, `What do you think about school?`, `How are you doing?`) now have one dominant canned phrasing and tied in both runs — the same over-drilled-category problem documented above for arithmetic/antonyms, just for a different set of prompts on the bigger model. A second failure mode showed up that the old model's tie-rate framing didn't capture: `Hey there`, `Would you rather be invisible or be able to fly?`, and `Is it better to be cautious or take risks?` did produce different text across temperatures, but incoherent non-sequiturs ("There are twelve months in a year.", "a bednac") rather than genuinely different valid answers — that's generation noise, not preference signal, and would poison comparisons just as badly as a tie.

- `PREFERENCE_PROMPTS` was trimmed to the nine prompts that showed real, coherent multi-reply variance in both test runs (`Tell me about yourself`, `What kind of AI are you?`, `Hello!`, `Good morning`, `How's it going?`, `Thank you`, `Thanks for the help`, `I have a question`, `What makes a good friend?`). No preference labels were collected or simulated as part of this check — real labeling with this refreshed list is still a task for the user, not this session.

## First independent capability evaluation (2026-09-09): a real, honest zero

Running Codex's `evaluate_capabilities.py` (issue #2) against the current 58.4M fine-tuned checkpoint (step 5000, hash `6fb04450...`, `data/instructions.txt` now including the facts category) produced **0% accuracy on every one of 5 categories** — comprehension, instruction-following, arithmetic, facts, and code reading (0/6 each, 30 questions total). This is strict, exact-match scoring (`response.strip() in expected_answers`) with greedy decoding, checked for training-data overlap (8-word exact-span matching against `data/instructions.txt`: zero hits — these are not memorized questions).

This looks worse than the live chat testing earlier tonight ("who was the first president" → correct; "6 plus 7" → correct), and the reason is informative, not contradictory:

- **Arithmetic**: every failure used two-digit numbers ("17 + 26", "91 - 37") outside the single-digit range the model was actually trained on. It still recognized the operation and produced the right *format* ("17 plus 26 is 21.") but the wrong number — confirming, again, that it pattern-matches memorized examples rather than computing, this time on numbers just slightly outside its training distribution rather than compact notation.
- **Facts**: some responses were factually correct but format-noncompliant under strict scoring — asked "Which planet is closest to the Sun? Answer only its name," it correctly said "Mercury is the planet closest to the sun," but the eval wanted exactly `"Mercury"`. This is a real, fair failure (the model can't follow an output-format constraint), not evidence the fact itself wasn't learned.
- **Comprehension and code reading**: genuine, unambiguous failures — multi-step reasoning ("who arrived last," "where is the marble now") and code-execution questions got unrelated memorized facts or garbled text, with no partial credit available. The model has no capability here at all; nothing in its training data teaches multi-step reasoning or code semantics.
- **Instructions**: same pattern as comprehension — asked to reverse letters or extract one word from a list, it falls back to unrelated canned facts. Output-format control was never trained as its own skill.

Honest takeaway: the model's real, verified capability is narrow-and-correct pattern completion on categories it was directly and repeatedly trained on (greetings, single-digit arithmetic in trained phrasings, a fixed set of facts) — and it generalizes close to zero beyond that, even to trivially adjacent variations (two-digit arithmetic, exact-output formatting, in-distribution facts phrased with a stricter answer format). This validates Codex's originally proposed roadmap: the next real capability gains come from comprehension/instruction-following/reasoning training data and much broader arithmetic ranges, not from more parameters or more of the same kind of narrow Q&A data.

## Fourth expansion (2026-09-09): full English Wikipedia (partial, 900K articles) -- corpus now ~7GB

With the streaming pipeline and fast tokenizer in place, a full (not "Simple") English Wikipedia extraction was attempted, using the same from-scratch wikitext stripper as before, but streaming the bz2 decompression directly from the network connection rather than saving the ~20GB+ compressed dump to local disk first -- this Mac only had 36GB free after a disk cleanup (freed from 7.4GB by clearing Xcode simulators, various app caches, and old installer files in Downloads), and the full dump plus its extracted output plus the eventual compiled corpus would not have fit otherwise.

The network reader includes automatic reconnect-with-HTTP-Range-header on any read timeout or connection drop, feeding the same `BZ2Decompressor` instance so decompression state survives a reconnect -- necessary for a job expected to run for hours. A hard 10GB safety cap was also set on the output file size, monitored by a separate watcher process, since the observed early extraction rate (534MB from the first 25,000 articles) extrapolated to an alarming ~140GB if it held for all ~6.8 million articles -- almost certainly an overestimate, since dump order appears to process long, well-developed articles before the long tail of short stub articles (the rate did slow noticeably as extraction progressed: 354MB for the second 25,000 articles, versus 534MB for the first).

**The run was killed by macOS for system-wide memory pressure at 900,000 articles / 6.6GB**, before hitting either the 10GB cap or the full 6.8M-article target -- the same root-cause pattern as the very first pretraining crash earlier in this project (multiple other applications, particularly several Chrome helper processes each using 500MB-800MB+, competing for this Mac's 8GB of RAM). The extraction script's own iterparse loop likely also contributed independently: clearing each processed `<page>` element's contents (`elem.clear()`) does not release the parent root element's growing list of now-empty Element object references over millions of iterations, a known category of memory growth with Python's `xml.etree.ElementTree.iterparse` on very large documents -- not fixed before the crash, since the crash happened before this was diagnosed.

The partial output was verified intact (valid UTF-8 via the streaming validator, no truncated multi-byte character at the cutoff) and treated as the final result for this session rather than risking a repeat crash chasing the remaining ~4.9 million articles, given the same memory-pressure pattern recurring twice now. 900,000 real, diverse English Wikipedia articles is still an enormous, genuine corpus addition on its own.

Final compiled corpus: 59 books + Simple English Wikipedia + 900K-article partial full English Wikipedia = **6,950,772,261 bytes (~6.95GB)**, compiled in 13.8 seconds by the now-streaming `compile_corpus()` (also fixed this session to copy sources in chunks rather than reading them all into memory and joining as one Python string -- necessary now that a multi-GB source file exists). The corpus-workspace cap was raised again, from 2GB to 10GB.

This is a real, honest, still-partial result: not literally "full Wikipedia," and the underlying capability evaluation in the section above was run before this expansion, so it does not yet reflect any benefit from this much larger and more encyclopedic corpus. The natural next step is pretraining a fresh model on this ~7GB corpus and re-running the same capability evaluation for a real before/after comparison.

## Live chat qualitative failures (2026-09-10): a real fact-splicing bug found by hand

Live testing the dashboard Chat tab against the 58.4M finetune (step 5000) surfaced four exchanges worth recording exactly, since each one is diagnostic of a different, specific failure rather than generic "small model is bad":

| Prompt | Reply | What's actually happening |
|---|---|---|
| `hello` | "Hi! Good to hear from you." | Correct — trained greeting category. |
| `can u help me with a math problem?` | "That's outside what I'm ready when you are." | Two memorized replies fused mid-sentence: a fallback reply ("That's outside what I've been trained on...") and a greeting reply ("...I'm ready when you are."). The model has no real boundary between the `fallback` and `help`/`greeting` categories — it interpolated. |
| `whatss 1+1` | "1 plus 1 is 14." | The double-s typo ("whatss" vs. the calculator's expected "whats") made `tools/calculator.py`'s `expression_from_message()` prefix regex miss, so the request fell through to the untrained language model instead of the deterministic tool. The model then produced the right *shape* ("N plus N is [number]") with a number unrelated to the actual input — the same no-real-arithmetic finding as the formal capability eval above, now also showing a real tool-routing fragility (typos bypass the calculator entirely). This is a `tools/calculator.py`/`server.py` robustness gap, not a training gap, and wasn't touched here since both files had unrelated in-progress uncommitted work at the time. |
| `whos the first president of the united states` | "George Water freezes at 0 degrees Celsius." | The most interesting bug of the four: the reply splices the start of the Washington fact with the tail of the water-freezing fact. Root cause is not prompt truncation — `prompting.py`'s `build_chat_prompt()` never cuts a turn mid-sentence, it only drops whole earlier turns that don't fit the 192-token budget. The likelier cause: this conversation had three unrelated turns of context (greeting, declined math request, wrong arithmetic) ahead of the real question, and `make_instructions.py`'s multi-turn training data, before this session, only ever generated exactly 2-turn conversations — near-zero training exposure to answering correctly with 3+ turns of unrelated clutter already in context, which is the actual shape of real chat usage. |

**Fix verified for the fourth failure, one for one:** `make_instructions.py`'s `build_two_turn()` was generalized to `build_multi_turn()` (2-4 turns instead of a fixed 2, still randomly unrelated pool entries, `target_multi` raised 2200 -> 4000), the corpus regenerated (24,906 blocks, 2.70MB), and the checkpoint finetuned 520 further steps (`train.py --data data/instructions.txt --finetune --loss-mode response`, held-out perplexity 6.11 -> 2.07). Freed real RAM first by quitting Chrome/Spotify (81MB -> 3.1GB free — see `research/TASKS.md`'s hazard log) rather than training under memory pressure. Re-sent the exact four-message conversation above through the live `/api/chat` endpoint afterward:

- `hello` -> "Hello! How can I help you?" — still correct.
- `whos the first president of the united states` -> **"George Washington was the first president of the United States."** — fixed. No more fact-splicing on this exact prompt.
- `whatss 1+1` -> "1 plus 1 is 19." — still wrong, as expected: this was never touched (no real arithmetic capability, and the calculator-typo routing bug in `tools/calculator.py` is out of scope here).
- `can u help me with a math problem?` -> "I'm not sure s to you Sunth even when you ; not sure — I'm a small model trained on a narrow set of examples, so I don't know that." — **still broken**, and arguably more garbled than before. This is honest evidence the multi-turn fix did not generalize to every splicing case: this one is a `help`/`fallback` *category-boundary* ambiguity (the model blending two legitimately-similar-sounding categories), which is a different root cause than the multi-turn-context-clutter problem the fix targeted, and needs its own separate data fix (clearer, more distinct phrasing/replies between `help` and `fallback`) rather than more multi-turn exposure.

Net result: a real, verified fix for the specific bug that was investigated, and an equally real, verified non-fix for a different bug that superficially looks similar. Recorded exactly as observed, not rounded up to "chat is fixed."

**Trained 1,000 further steps (step 520 -> 1520, held-out perplexity 2.07 -> 1.75) to actually bake in the new OPEN_ENDED category**, since a spot-check right after the first 520 steps found `/api/preferences/pair` giving genuinely mixed results: one clean, correct response and one garbled/blended response for "What makes a good friend?" (the category clearly wasn't fully learned yet). Re-checked after the extra 1,000 steps, and the honest picture got more interesting, not simply "better":

- **"Is it better to be cautious or take risks?"** now produces two different, complete, coherent, individually-valid answers at 0.5 vs. 0.9 temperature — genuine, labelable preference variance, the entire point of adding this category.
- **"What makes a good friend?"** converged to the *identical* answer at both temperatures — a tie again, and specifically the same over-drilled-category failure mode `WRITEUP.md` already documented for the original small-talk categories: more training steps made this one prompt's answer more confidently memorized, at the cost of the temperature-based variance that made it useful for preference labeling in the first place.
- **"Would you rather be invisible or be able to fly?"** produced two mostly-coherent but not-quite-clean responses (one trailed into "...more than 80.", the other into "...invisiwn before?") — partial progress, not fully resolved.
- **Re-tested the original fact-splicing fix — still holds**: "who was the first president" still correctly answers "George Washington..." after the extra training, so the earlier fix didn't regress.
- **"can u help me with a math problem?" changed shape but is still wrong**: now answers "See you later!" — grammatically clean (an improvement over the earlier word-salad output), but still the wrong category entirely, confirming this remains a distinct, unfixed `help`/`fallback`-boundary problem.

Honest takeaway: more training steps on a bigger, more diverse instruction pool doesn't uniformly help — it can fix one category's coherence while re-breaking another category's *variance*, simultaneously, in the same run. This is the same tie/over-drilling dynamic this project's RLHF section already found for the original categories, now observed happening live to a brand-new category within a single training run, not just across categories. `PREFERENCE_PROMPTS` in `server.py` should be updated to include the categories that now show genuine variance (at minimum the risk/caution prompt) but not the ones that collapsed to ties (the good-friend prompt) — left for whoever owns that file next, since it currently has unrelated uncommitted changes.
