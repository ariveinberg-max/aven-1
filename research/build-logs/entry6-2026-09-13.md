# Build log — Entry 6

The rest of Day 15: closing out KTO's oldest open item, and a real mechanism found for a puzzle that's been flagged twice.

## KTO, retrained and finally live-inspected
KTO had been sitting as this project's oldest unresolved item since Day 10 — trained, but never actually checked against real generations, only its own training metric. Retrained it on the current dataset (562 comparisons, up from 162 at its first run): held-out accuracy stayed noisy across steps (0% → 87.5% → 62.5% → 100% → 50%), same instability pattern the reward model has shown across retrains.

Then did the inspection that had been overdue: compared 8 prompts, greedily, against the currently active checkpoint. 7/8 were clean — but "Can you help me with a math problem?" produced a real generation glitch, a duplicated trailing text fragment. The frozen capability suite showed 0 regressions against the same checkpoint and would have looked completely clean — it doesn't cover that prompt, so it was blind to the exact defect live-checking caught. This is now the second RLHF method (after PPO, twice) where the metric looked fine or plausible while a live check caught something real the automated suite structurally can't see. **Not promoted.** Reward-model+RAFT remains the only method with a clean record across every round tried on this project so far.

## Why KTO's z0 sits at 0.000
A smaller but genuinely satisfying find. KTO's reference point (z0) had printed as almost exactly 0.000 across two separate training runs, flagged as unexplained both times. Instead of flagging it a third time, tested it directly: loaded the finished policy against its own pre-training starting point and recomputed the raw, *unclamped* reward the code normally floors at zero. Every one of three real batches came back negative (-0.719, -0.583, -0.003).

That's the actual mechanism: the code's `max(0.0, ...)` clamp is doing exactly what it was written to do, it's just triggering almost every step, because KTO's own training update concentrates each prompt's probability mass onto its own target response — which comes at the expense of unrelated responses' probability, exactly what a genuinely mismatched (prompt, unrelated-response) pair measures. Not a bug. Closed with a verified mechanism instead of an open question.
