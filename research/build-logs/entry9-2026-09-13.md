# Build log — Entry 9

A third PPO attempt that reverses an earlier hopeful note, and a real diagnosis of why the automated safety net keeps missing exactly the failures this project keeps finding.

## PPO's third attempt — the worst one yet
This project's own prior note said PPO was "no longer blocked by the specific data-scarcity reason the original attempt failed on" once the dataset passed 162 comparisons. Retrained the reward model on the current 617-decided pool (252 usable train pairs) and tried again at `ptx_coef=0.5`, an untested coefficient.

The result reverses that hopeful framing directly: more data did not fix PPO here. If anything, this was the worst of three attempts. Reward stayed mostly negative across training with no clean trend, and — for the first time — the training log itself showed real warning signs before the checkpoint was even saved: KL and entropy both spiked sharply in the final third of the run. Live-checking confirmed it: "Hey there" produced nonsense arithmetic, "I have a question" returned a response bled over from a completely different prompt, and the known day-of-week bug got measurably worse rather than just persisting. Not promoted.

Three attempts, three data scales (34, 162, 252 comparisons), four coefficients (0, 0.05, 0.2, 0.5) — never once a clean result. That's now the actual finding: not "try a different coefficient next time," but that PPO isn't a good fit for this project's data scale, full stop, until something structural changes.

## Why the safety net keeps missing exactly these failures
The frozen capability suite has shown 0 regressions against real, live-verified defects three separate times now (PPO twice, KTO once) — every prior note wrote this off as "the suite doesn't cover this" without ever checking why.

Checked it directly: all 30 cases across all 5 categories (comprehension, instructions, arithmetic, facts, code reading) are task-oriented, exact-match prompts. Zero conversational coverage. Every single regression this project has actually caught has been in the one category the suite structurally cannot see — greetings, thanks, and help-requests.

Read Ribeiro et al. 2020's CheckList framework, the standard method for exactly this problem: organize test coverage by linguistic capability, not just task type. Concrete recommendation: add a conversational category to the suite (greetings, gratitude, help-requests), scored by an LLM judge rather than forced into exact-match — this project already has that judging mechanism in `regression_checker.py`, it just isn't a mandatory step before every promotion decision. Folding it in would catch defects like today's PPO regressions and KTO's glitch automatically, instead of relying on a human remembering to spot-check by hand every time.
