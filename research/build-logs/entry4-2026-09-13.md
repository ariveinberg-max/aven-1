# Build log — Entry 4

Covers Days 8–14: the widest-ranging entry yet — a labeling-workflow change, a full recovery of Aven-2's training, a third RLHF method, a second reward-model/RAFT cycle, the first real PPO attempt, the first published model card, and a first real step toward outside compute funding.

## RLAIF, measured before deciding
Manual preference labeling is tedious, and it was tempting to hand it entirely to an AI judge. Measured that idea before trusting it: ran a local judge (`llama3.2:3b`) against 30 real human labels on the same prompt pairs.

- Overall agreement: 53.3% — barely above chance for a binary choice.
- But the disagreement wasn't random: it clustered almost entirely on short small-talk prompts (greetings, farewells), where two responses are often subtly similar. On substantive prompts (help requests, open-ended questions), agreement was close to 100% in the same test.

**Decision, backed by the measurement**: split the labeling pool instead of switching wholesale. Small-talk prompts stay human-only; substantive prompts get auto-labeled by a new scoped agent (`agents/rlaif_auto_label.py`). Every row in `preferences.db` now carries a `source` column (`human`/`ai`) so the two are never silently blended without a record of which is which. Run for real, one AI-labeled pick was caught during a spot-check choosing a genuinely garbled response over a clean one and manually removed — honest confirmation the mechanism is meaningfully better than chance on its scoped bucket, not perfect.

Since the crash-loop fix reported in Entry 3: step 11,260 → 19,080+ (~7,800 more steps), perplexity down from ~38 to **~24.6** — a large, sustained improvement, not just "no longer crashing."

## KTO, built and run for the first time
A third RLHF method alongside DPO and reward-model+RAFT: KTO (Kahneman-Tversky Optimization), which trains on binary desirable/undesirable examples instead of paired comparisons. Derived directly from existing preference pairs (162 pairs → 324 examples), no new labeling UI needed.

Caught a real bug in review before ever running it: the first draft's reference-point (z0) calculation reordered already-computed rewards instead of scoring genuinely mismatched prompt/response combinations — meaningless, since mean is permutation-invariant. Fixed with real mismatched-pair forward passes. Result: 62.5–87.5% held-out accuracy, noisier than DPO but in the same range. Saved separately, not yet live-inspected against generations — an honest open item.

## Second reward-model + RAFT cycle
Retrained the reward model on 162 usable pairs (up from 88) — held-out accuracy landed at 60.53%, *lower* than the prior cycle's 75% despite nearly double the data. Reported as measured, not smoothed over.

RAFT's own candidate diversity collapsed independently: average spread dropped from 7.895 to 1.726, with 16 of 19 prompts showing zero spread. Root cause: `raft.py` has its own separate temperature schedule that never received the diversity fix already applied to the labeling tool's pair-generation endpoint — the same underlying phenomenon (a confident model stops diverging at low temperature), hitting a second, independent piece of code. Logged as a real, not-yet-fixed gap.

All 19 candidates were clean this round. Trained via an isolated output directory, live-checked 8 prompts (7/8 identical), verified 0 regressions against a freshly-regenerated same-code baseline (the prior baseline was correctly rejected by `compare_capabilities.py`'s own code-version check). Promoted.

## PPO, actually run this time
Reviewed the project's prior PPO/ptx finding (34 comparisons, no coefficient both stable and effective), then ran it again with ~5x more data: `ptx_coef=0.2`, a genuinely new test point. Reward was noisy across 20 iterations, KL stayed well under the collapse limit — but live-checking found a real regression: "Thank you" produced incoherent, hallucinated text. The frozen capability suite showed 0 regressions and would have looked completely clean — it doesn't cover greeting/thanks-style prompts, so it was blind to the exact thing live-checking caught. Not promoted.

Found and fixed a separate gap along the way: none of `dpo.py`/`kto.py`/`ppo.py`'s saved checkpoints included a `step` field, so `evaluate_capabilities.py` had silently never run against that session's DPO or KTO results either. Fixed all three; patched the two already-saved checkpoints in place.

**Why, precisely**: PPO trains on online rollouts from the current policy every iteration; DPO/KTO/RAFT train on static, offline data reused directly — a structural difference, not an implementation detail. The literature is direct on this: PPO needs substantially more training episodes to converge in sparse-experience regimes, and 162 comparisons over 20 iterations is exactly that regime. This is the second PPO attempt on this project, at two very different data scales, both showing the same instability RAFT/DPO/KTO don't share.

**One number for the headline**: four real RLHF methods now exist side by side (reward-model+RAFT, DPO, KTO, PPO), each tested against the same growing dataset, each with honest results reported rather than the best one cherry-picked. Three of four produced live-verified-clean or nearly-clean results; PPO produced a real regression twice, at two different data scales — and the literature explains exactly why.

## First real free-credit research, and a real org-side lesson
Shortlisted three free-credit programs — GitHub Student Developer Pack, Hugging Face community GPU grants, Google Cloud research credits — and evaluated each against what actually matters here: GPU compute, not tooling. Hugging Face's grant isn't reachable yet (gated on publishing an actual model demo, a Phase 1 milestone not yet hit). Google Cloud's program doesn't fit the current stage. GitHub's pack is available now, mainly useful for Copilot and private repos, with its cloud-credit tier's GPU eligibility still needing verification.

Applied for real. First submission was rejected — GitHub's automated check requires the billing-account name to match the name on the uploaded proof-of-enrollment (a school ID); fixed by correcting the legal name in billing settings and resubmitting. Separately tried adding the school-issued email for auto-verification, which never arrived — traced to the school's Google Workspace domain almost certainly blocking external mail from `github.com` at the admin level, unfixable from this side. Dropped that path rather than escalate to school IT for a nice-to-have; the corrected application is now in manual review. A small, real example of a principle this project already applies to model results: verify the actual blocker instead of guessing at one.
